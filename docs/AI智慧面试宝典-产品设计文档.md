## 一、产品概述

### 1.1 一句话定位

像做题一样系统化训练面试：**海量结构化题库 + 智能出题 + 错题强化 + 语音模拟面试**，题目由 AI 根据**你的简历**和**目标岗位的真实 JD** 动态生成，每题附参考回答与深度解析。

### 1.2 解决的核心痛点

| 痛点 | 现状 | 本产品的解法 |
|---|---|---|
| 面经/八股文是通用题，不贴合个人经历 | 网上题库千人一面 | 基于简历逐段深挖，生成「只有你会被问到」的题 |
| 不知道目标岗位真实考什么 | 靠面经碎片拼凑 | 检索 BOSS 直聘真实在招岗位 JD，反推考点 |
| 投递前没有针对该公司/岗位的精准准备 | 一份简历海投 | 输入岗位链接/截图/文本，生成「JD × 简历」交叉定向题库 |
| 刷完题不知道对错、没有反馈 | 死记硬背 | 每题附参考答案 + 评分点解析 + 错题本循环强化 |
| 训练没有节奏、难以坚持 | 三天打鱼 | 今日学习计划 + 连续打卡 streak + 复习提醒推送 |

### 1.3 目标用户

- 应届/实习求职者（无面试经验，需要系统化题库与模拟考试）
- 1~5 年经验跳槽者（项目深挖、场景设计题是短板）
- 转行/跨岗求职者（不知道新岗位问什么，需要岗位驱动的考点探测）

### 1.4 产品形态（V2.0 确定：双端并行）

| 端 | 载体 | 承担场景 |
|---|---|---|
| **Web 端** | Next.js（PC 浏览器） | 重操作场景：简历上传/解析、岗位检索、JD 定制出题、看板管理、深度报告查看 |
| **移动端** | 小程序优先（Taro），App 后置 | 碎片化场景：每日刷题、错题复习、语音模拟面试、看板速览、推送提醒 |

双端共用同一套后端 API 与账号体系，页面信息架构对齐（见第八章），数据实时同步（Web 上传简历 → 手机继续刷题）。

## 三、核心功能详细设计

### 3.1 首页 · 今日学习计划（V2.0 新增，原型 P1 核心组件）

首页是每日打开的「学习中枢」，双端结构一致，包含四块：三大引擎入口卡、今日学习计划、本周图表、核心统计（本周刷题 128 / 正确率 76% / 待复习 23 式三卡）+「开始今日刷题」主按钮。

**今日学习计划规则：**

- 每天凌晨由 AI 结合用户状态自动生成 3~5 项任务，用户可手动添加/删除（原型提供「添加学习计划」输入框），右上角显示完成度（「已完成 3/5」）；
- 任务类型与默认时长预估（与原型一致）：

| 任务类型 | 示例（原型） | 时长预估 | 数据来源 |
|---|---|---|---|
| 刷题任务 | 产品经理核心题集 · 刷 20 题 | 15 分钟 | 进行中的题集 + 薄弱知识点 |
| 错题复习任务 | 错题复习 · 艾宾浩斯第 2 天 | 10 分钟 | 错题本当日到期队列 |
| 模拟面试任务 | AI 模拟面试 · 行为面专场 1 场 | 25 分钟 | 看板面试日期临近时权重提高 |
| JD 定制任务 | JD 定制题集 · 字节跳动后端岗 | 20 分钟 | 未刷完的定向题集 |
| 简历体检任务 | 简历体检 · 查看 AI 优化建议 | 5 分钟 | 新简历上传后触发一次 |

- 「开始今日刷题」按计划顺序自动进入第一个未完成任务；
- 完成度与 streak 联动：当日计划完成 ≥ 2/3 记为打卡成功，横幅展示「连续学习 12 天 · 今日已完成 3/5 项计划」。

### 3.2 题库中心（结构化训练体验，原型 P2/P9/P10/P11）

#### 3.2.1 题目数据模型（统一题型协议）

所有引擎生成的题目最终归一化为同一结构，保证刷题/考试/错题本等通用能力复用：

```json
{
  "question_id": "uuid",
  "source": "resume | job_search | jd_target | system_bank",
  "type": "single_choice | multi_choice | judge | short_answer | scenario",
  "category": "专业技术 | 项目深挖 | 行为面试 | 系统设计 | HR综合 | 公司认知",
  "knowledge_tags": ["Redis", "缓存穿透", "分布式锁"],
  "difficulty": 1,
  "stem": "题干……",
  "options": ["A. …", "B. …", "C. …", "D. …"],
  "answer": "A",
  "reference_answer": "参考回答（简答/场景题的标准作答框架）",
  "explanation": "解析：为什么选 A，面试官想考察什么，答错说明哪块薄弱",
  "interviewer_intent": "考察意图说明",
  "follow_up": ["面试官可能的追问 1", "追问 2"],
  "related_resume_anchor": "该题由简历中的哪段经历/技能触发（可溯源）",
  "related_jd_anchor": "该题对应 JD 中的哪条要求（可溯源）",
  "created_at": "…",
  "quality_score": 0.92
}
```

**设计要点：**
- 客观题（单选/多选/判断）用于「刷题快感 + 知识点扫盲」；主观题（简答/场景）用于「输出训练」，配 AI 评分。
- `related_resume_anchor` / `related_jd_anchor` 实现「题目可溯源」，用户在刷题页可点击跳转到简历原文 / JD 原文，建立信任感。
- `follow_up` 追问链供「AI 模拟面试」直接复用。

#### 3.2.2 题库中心页（原型 P2）

- 顶部统计：「共 12 个题集 · 486 道题 · AI 持续为你生成」；
- 搜索题集 + 「新建题集」按钮；
- 来源筛选 chips：全部 / 简历生成 / 岗位检索 / JD 定制 / 模拟面试；
- 题集卡片：来源徽章、标题、题数、更新时间（「更新于 2 小时前」）、进度条、完成 x/y、操作按钮（继续刷题 / 再来一遍 / 开始刷题），刷完的题集显示绿色「已完成 40/40」。

#### 3.2.3 刷题模式与交互（原型 P9/P10 细化）

| 模式 | 说明 |
|---|---|
| 专项练习 | 按 category / knowledge_tag 筛选，10/20/50 题一组 |
| 顺序练习 | 按生成顺序通刷一套题 |
| 随机练习 | 乱序抽题，防位置记忆 |
| 背题模式 | 直接显示题目+答案+解析，快速过 |
| 攻克难题 | 只刷 difficulty ≥ 3 或历史正确率 < 60% 的题 |
| 模拟考试 | 限时组卷（默认 20~30 题/45 分钟，题型按比例混合），交卷出报告 |

**刷题页交互（原型 P9）：**
- 顶部：退出 / 第 N/M 题 / 倒计时（临近超时转橙色）；顶部细进度条；
- 题目卡带题集徽章；选项点击即选中高亮（练习模式即时判对错并变色反馈）；
- 底部「上一题 / 下一题」；**答题卡**数字格区分已答/未答/当前题，明示「已答 2 题 · 未答 18 题 · 交卷前可修改答案」。

**题目详情页（原型 P10）：**
- 正确答案徽章 + **全站答对率**（如「全站答对率 62%」，见 3.7 统计服务）；
- 选项正误着色（绿色正确 / 红色误选）；
- 「答案解析」与「参考回答」双 tab；参考回答给「作答要点」框架；
- 「加入错题本」手动入口（自动收录之外允许主动强化）+ 右上角收藏。

#### 3.2.4 模拟考试报告（原型 P11）

- **分数圆环**（如 82 分）+「产品经理模考 · 超越全站 74% 的考生」；
- 维度分条形（如：专业知识 88 / 案例分析 80 / 行业认知 70）；
- 正确率 + 总用时（如 76% / 18:24）；
- 「查看错题解析」入口 → 薄弱知识点 TOP5 + 一键生成「补强练习卷」；
- 与历史模考成绩趋势对比。

### 3.3 引擎 A：简历智能分析出题（原型 P3）

**输入**：用户上传简历（PDF / Word，≤10MB；支持图片 OCR / 纯文本粘贴）
**输出**：360° 个人专属题库（原型示例：约 120 题）+ 能力维度评估 + 简历体检报告

#### 处理流水线

```
简历上传（三步 stepper：1 上传简历 → 2 AI 解析 → 3 生成题库）
  → ① 文档解析（PDF/DOCX 文本抽取；图片走 OCR；统一转结构化文本）
  → ② 简历结构化（LLM 抽取：基本信息/教育/技能栈/项目列表[背景-职责-技术-成果]/实习/证书/自我评价）
  → ③ 能力维度评估 + 题量预估（解析完成即展示，见下）
  → ④ 考点挖掘规划器（Planner）：按覆盖矩阵规划出题任务
  → ⑤ 并行出题（Generator，多批调用，每批一个维度）
  → ⑥ 质量校验（Critic）：去重、事实校验（不得超出简历声称的范围）、答案正确性校验
  → ⑦ 入库 + 简历体检报告生成（见 3.6）
```

#### 能力维度评估（V2.0 新增，原型明确展示）

- 解析完成后即时输出 4 维评分条形图，按岗位方向配置维度集（产品经理示例：项目管理 85 / 数据分析 72 / 沟通协作 90 / 行业认知 68），每维一句诊断；
- 同步展示：工作年限、目标岗位、预计生成题量（「约 120 题」）；
- 评估结果作为 Planner 出题权重输入：低分维度多出 L1/L2 基础题，高分维度多出 L3 深挖题；
- 题量预估公式：`N ≈ 项目数 × (12~18) + 技能数 × (3~5) + 行为/HR 固定 12`；生成设置允许调档（精简 40 / 标准 80 / 深度 120+）。

#### 覆盖矩阵（保证「广度和深度」）

| 维度 | 说明 | 占比建议 |
|---|---|---|
| 技能八股 | 简历技能栈逐项展开：原理、对比、选型、踩坑 | 25% |
| 项目深挖 | 每个项目：架构、难点、权衡（为什么这么设计）、数据量/性能数字、如果重做怎么改 | 30% |
| 场景设计 | 由项目延伸的真实场景题（如"你的系统 QPS 翻 10 倍怎么办"） | 15% |
| 行为面试 | 基于经历的行为题（冲突、压力、失败、领导力），STAR 框架 | 15% |
| HR 综合 | 职业规划、离职原因、期望薪资、优缺点——结合简历实际空窗/跳槽记录定制 | 10% |
| 压力/陷阱题 | 针对简历中的疑点（时间断档、项目描述夸大风险、转行逻辑） | 5% |

页面底部固定注释「覆盖 L1 基础 → L3 深度 · 每题附参考回答 + 解析 · 贴合真实面试场景」。

#### 出题 Prompt 设计原则（关键）

1. **锚定原文**：每题必须引用简历中的具体段落作为出题依据（`related_resume_anchor`），禁止生成简历未覆盖的「虚空题」。
2. **深度递进**：同一知识点生成 L1（概念）→ L2（原理/对比）→ L3（权衡/实战/故障排查）三档深度。
3. **真实感**：以「资深面试官」人设生成，题干使用真实面试口吻（"我看你简历上写了 XX，能具体讲讲当时为什么……"）。
4. **答案三件套**：参考答案 + 评分要点 + 常见错误回答示例。

### 3.4 简历体检报告与 AI 一键优化（V2.0 升级为独立功能，原型 P12）

原型将「简历体检」从附属产出升级为完整功能闭环：

```
简历体检报告
  ├─ 总分（0~100）+ 评语（原型示例：86 分「整体优秀 · 可冲刺一线大厂简历筛选」）
  ├─ 简历亮点（✓ 项目经历均有量化结果：DAU +35%、转化率 +12%；
  │            ✓ 技能栈与目标岗位 JD 高度匹配）
  ├─ 待改进清单（! 第二段经历缺少背景与职责描述；自我评价偏泛，建议替换为差异化标签；
  │              教育时间线存在 2 个月空窗，需补充说明）
  ├─ AI 优化建议（具体改写示范：「负责 XX 项目」改写为 STAR 结构：背景→行动→量化结果；
  │              数据产品经验前置突出，匹配 JD 定向岗位）
  └─ 【AI 一键优化简历】→ 生成优化版简历（新版本入简历管理，可对比、可下载 DOCX/PDF）
```

实现要点：体检与出题共用同一次简历解析（一次 LLM 解析多路消费：题库 Planner + 体检评分器）；一键优化以「体检结论 + 原简历结构化数据」为输入重写，保留原版为历史版本（原型「我的页 · 简历管理 · 2 份」）。

### 3.5 引擎 B：岗位方向检索出题（接入 boss-agent-cli，原型 P4）

**输入**：目标岗位关键词（如「产品经理」）+ 城市 + 经验要求（可选）
**输出**：该岗位方向的通用面试题库（市场视角：当前真实在招岗位都在要求什么）

#### 集成方案

采用 [boss-agent-cli](https://github.com/can4hou6joeng4/boss-agent-cli) 作为岗位检索层。该项目提供统一 CLI / MCP / Python API 三种接入方式，stdout 输出 `{ok, data, pagination, error, hints}` JSON 信封，天然适合 Agent 编排。

**推荐接入方式（二选一）：**

1. **MCP 方式（推荐）**：将 boss-agent-cli 的 MCP Server 挂到我们的 Agent 编排层：
   ```json
   { "mcpServers": { "boss-agent": { "command": "uvx", "args": ["--from", "boss-agent-cli[mcp]", "boss-mcp"] } } }
   ```
2. **Python SDK 嵌入**：
   ```python
   from boss_agent_cli import AuthManager, BossClient
   with BossClient(AuthManager(...)) as client:
       result = client.search_jobs("Java后端", city="深圳")
   ```

#### 处理流水线（含原型新增的生成设置）

```
用户输入岗位关键词 + 城市 + 【生成设置（原型 chips）：题量(默认50) / 难度(混合|L1|L2|L3) / 附参考答案+解析(默认开)】
  → ① boss search "<关键词>" --city <城市>   （JSON 信封返回岗位列表，含 security_id）
  → ② 智能采样 Top N（默认 15~20 个岗位，按公司规模/薪资带分层抽样，避免单一公司偏差）
  → ③ boss detail <security_id> × N          （逐个取 JD 详情；结果落本地缓存，TTL 7 天）
  → ④ JD 聚合分析（LLM）：
        - 高频技能要求 TOP 榜（"80% 的岗位要求 Redis"）
        - 高频职责场景
        - 薪资带与要求差异（初级 vs 资深考点不同）
  → ⑤ 按聚合结果 + 生成设置出题（市场通用卷）+ 若用户已有简历则自动叠加简历维度
  → ⑥ 输出「岗位市场考点报告」+ 配套题库
```

#### 用户体验输出（与原型一致）

- 搜索结果岗位卡：岗位名 + 橙色薪资（如 25-50K·16薪）+ 公司·城市·经验·学历 + 业务标签（B端产品/增长策略）+「生成题目」按钮；
- 页面固定展示数据来源声明：「数据来自 Boss 直聘 · 实时检索 · 缓存 7 天」，建立透明度与信任；
- **考点地图**："该岗位当前市场上最常被要求的 10 项技能" 可视化榜单；
- **题库**：按「必备高频题 / 加分项题 / 差异化题」三档组织；
- **合规说明**：boss-agent-cli 采用用户主动登录态、请求节流（高斯延迟）、结构化错误恢复，命中平台风控会停止并返回恢复指令。我们侧仅做**只读检索**，不做批量采集/打招呼等动作，频率受控。

### 3.6 引擎 C：JD 精准定制（V2.0 扩展为三输入通道，原型 P5）

**输入通道（原型三 tab）**：
1. **粘贴链接**：解析 BOSS 岗位 URL → 提取 security_id / job_id → `boss detail` 精确取全量 JD、薪资、公司、福利；
2. **上传截图**：多模态 LLM 视觉解析 → 提取岗位名/公司名/城市/关键 JD 文本 → `boss search "<岗位名> <公司名>"` 反查匹配（公司名+岗位名相似度）锁定目标岗位 → `boss detail`；
3. **粘贴文本**（V2.0 新增）：用户直接粘贴 JD 文本 → LLM 结构化，无需检索，覆盖非 BOSS 渠道岗位，同时作为链接失效/截图识别失败时的终极兜底通道。

**解析结果面板（原型右栏）**：岗位名 + 公司·部门（如「字节跳动 · 电商平台部」）、**简历匹配度徽章**（如 78%，有简历时实时计算）、公司背景摘要（如「成立于 2012 年，旗下拥有多款亿级用户产品，电商业务处于高速增长期」）、JD 核心要求 chips（产品规划/数据分析/跨团队协同/增长策略/电商经验优先）。

**「结合我的简历生成」开关（V2.0 新增交互）**：
- 开（默认）：出题 = JD 直接映射题 + 简历×JD 交叉题 + 公司认知题 + 反向提问建议，输出匹配度报告；
- 关：仅按 JD 出通用定向题（用户不想暴露简历或未上传简历时的降级路径）。

**汇合后出题规划（开关开启时）：**
```
JD 结构化（职责/硬性要求/加分项/团队与业务线）
  + 公司背景情报（公司规模、融资阶段、主营业务、技术栈传闻、面经聚合——公开信息 RAG 检索）
  + 简历交叉分析（匹配项 / 缺口项 / 风险项）
  → 出题规划器：生成四类题
       ① JD 直接映射题：每条核心要求 → 2~3 题（你简历匹配上的 → 深挖题；没匹配上的 → 补课题 + 应对话术）
       ② 简历×JD 交叉题：面试官拿你简历对着 JD 会问什么（"你简历做的是 A 业务，我们是 B 业务，你怎么迁移经验？"）
       ③ 公司认知题：对该公司业务/产品/竞对的理解
       ④ 反向提问建议：面试结尾「你还有什么问题」的高质量提问清单
  → 输出「岗位冲刺包」：定向题库 + 岗位匹配度评分 + 缺口清单 + 应答策略建议
```

#### 关键设计：匹配度报告

```
岗位匹配度：78%
✅ 强匹配（3 项）：微服务经验、MySQL 优化、团队协作
⚠️ 弱匹配（2 项）：K8s 只在课程项目用过 → 生成「补强突击题包」
❌ 缺口（1 项）：无支付领域经验 → 生成「业务知识速成材料 + 诚实应对话术」
```

这是本产品区别于通用刷题 App 的最核心交付物。

### 3.7 全站统计服务（V2.0 新增，支撑原型两处数据）

原型两处依赖全站数据：题目详情「全站答对率 62%」、模考报告「超越全站 74% 的考生」。实现：

- 答题事件异步入仓（Celery 聚合：Redis 实时计数器 + 每日批量落库），答对率按题维度计算；
- **上线时序（V2.1 修正）**：轻量答对率统计（Redis 计数 + 低样本保护）随 **Web 一期**上线——因为题目详情页一期即展示答对率，统计能力必须同期就绪；模考「同岗位分桶百分位」随 **Web 二期**模考功能上线；
- 低样本保护：作答次数 < 100 的题目不展示答对率，避免误导；
- 模考百分位按「同岗位方向」分桶计算（产品经理考生 vs 产品经理考生），样本不足退化为全站；
- 隐私：仅聚合统计，不暴露个体数据。

#### Web 端承载方式（V2.3 补）

原型 Web 版顶栏右侧常驻用户头像但未定义其落地页，导致账号管理、通知、数据导出、注销在 Web 端（重操作场景）无承载入口。V2.3 明确：**点击顶栏头像进入 P14「我的」页**，与移动端 P13 信息架构同构、共用同一套 API，**不新增顶栏导航项**（保持原型 8 项导航不变）。设置项按期分批落地：

| 批次 | 落地项 | 理由 |
|---|---|---|
| **一期（W1~W4）** | 个人资料（头像/姓名/目标岗位·年限）、三统计卡、退出登录、**注销申请（一键删除全部数据）**、复习提醒时间 | 账号体系（微信 + 手机号登录）与错题复习提醒均在一期；注销是第五章合规「提供一键删除全部数据」的兑现入口，不可后置 |
| **二期（W5~W7）** | 学习报告入口、简历管理 · N 份（各版本挂体检报告）、通知管理、数据导出 | 承载功能本身在二期交付（周报 / 简历体检 + 多版本管理 / 通知中心），入口与功能同期上线，避免空壳菜单 |

- **注销流程（双端一致）**：二次确认（须手动输入「注销」二字才可提交，防误触）→ 校验无进行中的出题任务（有则 409 拒绝，避免任务产物写回已删数据）→ 写入 7 天冷静期（`cooling_off_until`，期内可撤回且数据保持原样；**重复申请不重置倒计时**）→ 到期异步清理（PG 业务记录 + 对象存储简历文件物理删除 + `agent_artifacts` 用户产物）→ 逾期不可恢复，清理后账号进入「已注销」态，资料与偏好接口返回 410。
- **清理范围须在确认弹窗内逐条明示**（对齐第五章知情同意）：个人资料与账号绑定 / 题集与刷题进度、答题事件明细 / 错题本与复习调度队列 / 收藏与笔记 / 简历原文件与解析产物 / 学习统计与周报数据。
- **一期实现口径（V2.5 补）**：一期内存 Mock 无定时器，由 `POST /api/me/deactivation/execute?force=true` 作为手动触发入口验证清理链路；接 PG 后改为定时任务扫描 `cooling_off_until` 到期项执行，`force` 入口收敛到管理端。

### 4.3 出题编排 Agent（LangGraph 状态机）

```
[输入源解析] → [Planner: 出题规划] → [并行 Generator × N]
      → [Critic: 质量校验] --不通过--> [回炉重新生成]
      → [答案自检: 客观题答案一致性二次验证]
      → [Embedding 去重（与历史题库相似度 > 0.9 的丢弃）]
      → [入库 + 流式通知前端出题进度]
```

- 出题是**长任务**（60~120 题，分钟级），必须异步 + 流式进度（"已生成 23/80 题 · 当前维度：项目深挖"），前端逐步渲染**已生成的题立即可刷**。
- **客观题答案必须二次校验**：用独立 prompt 让模型只做「这道题选什么」，与生成答案比对，不一致则人工规则兜底（标记待审），这是题库类产品准确性的生命线。
- 生成失败维度自动重试 2 次，仍失败则跳过并在报告中明示「点击重新生成」；中途可退出，后台继续，完成后推送通知。

#### 4.3.1 Agent 状态、记忆与容错（V2.2 新增）

1. **任务级 Checkpoint（关键补强）**：LangGraph 每个 Node 执行完即把 state 快照写入 PostgreSQL（`agent_checkpoints(task_id, node, state_json, updated_at)`）。Celery worker 崩溃 / OOM / 发版重启后，任务从最近 Checkpoint 续跑而非从头重出——一次 80 题任务重跑就是一笔可观的 token 损失，且「出题到 90% 断掉重来」是用户最不可忍的体验事故。SSE 断线重连解决的是「前端看不到进度」，Checkpoint 解决的是「后端从头再算」，两者缺一不可。
2. **LLM 结构化输出强制约束**：所有出题 / 解析 / 评估调用强制走 JSON Schema（Pydantic 模型 + function calling / structured output），解析失败自动重试 2 次，仍失败则该题标记「待审」不落库，**禁止裸文本正则抽取 JSON**——这是题目结构完整性的第一道防线。
3. **上下文裁剪（Agent 记忆的 token 预算）**：批间共享的记忆不是全量历史题目，而是「简历结构化摘要 + Planner 规划结果 + 已出题摘要（knowledge_tags + 题干首句列表）」，单批 prompt 控制在 8K token 内；这样 Generator 批次间既有记忆（防重复出题）又不受上下文长度限制。
4. **Agent 间上下文传递（产物复用）**：三引擎的结构化中间产物（简历解析 JSON、JD 聚合报告、公司背景摘要、匹配度中间结果）统一落 `agent_artifacts` 表并带缓存键，供简历体检 / 计划生成 / 匹配度报告复用——一次解析多路消费是 4.6 缓存策略的落点，也是成本控制的根基。
5. **boss-agent-cli 服务端化改造（V2.2 修正）**：原设计中「用户主动登录态 + ~/.boss-agent 本地状态（SQLite/文件）」是单机 CLI 场景，直接搬到服务端存在两个问题：① 多用户产品不能要求每个用户登录 BOSS，且用户账号池不可控；② 本地 SQLite 文件在多 Celery worker 并发下会锁表损坏。修正为：**平台运维受控检索账号（只读、低频、请求节流沿用其高斯延迟机制），登录态与 JD 缓存统一迁移到服务端 Redis + PostgreSQL（`jobs_cache` 表）**，boss-agent-cli 仅作为检索协议实现被 SDK 嵌入，不使用其本地状态存储。

### 4.6 LLM 成本与质量控制

- **分层用模**：解析/校验/去重用轻量模型；出题/体检/一键优化用主模型；截图解析用多模态模型。
- **缓存优先**：相同 JD（security_id 命中缓存）+ 相同简历版本直接复用历史套题；同岗位关键词的市场题库按「周」粒度共享缓存（脱敏后），热门岗位可摊薄 90% 出题成本；TTS 题目音频预合成缓存。
- **质量闭环**：用户对题目可点「题目有误 / 答案有误」，反馈进入 Critic 再训练样本池；客观题答案双模型交叉验证，不一致题降权或人工审核；全站答对率异常监测（某题答对率 < 5% 自动标疑人工审）。

#### 4.6.1 模型配置管理端（V2.3 新增）

**定位**：平台侧内部工具（`/admin/models`），仅管理员可见，**不向 C 端用户开放模型选择**。

为何不做用户侧模型配置：4.6 的分层用模与缓存摊薄（缓存键 = hash(**模型标识** + Prompt 版本 + 输入摘要，见 4.7）依赖平台统一口径；若用户各自选模型，缓存无法共享、成本不可控、题目质量口径不一致。用户侧可配置的只有业务级「生成设置」（题量档位 / 难度 / 是否附参考答案+解析，见 3.3、3.5、3.6）。

**配置项（对应 4.1 架构图 LLM 层的四类分层 + 语音）**：

| 分层 | 用途 | 可配项 |
|---|---|---|
| 主模型 | 出题 / 简历体检 / 一键优化 | 供应商、模型名、API Key、base_url、temperature、max_tokens、超时、并发上限、fallback 备用模型 |
| 轻量模型 | 答案二次校验 / 结构化解析 / 去重判定 | 同上 |
| 多模态模型 | JD 截图解析 / 简历扫描件 OCR | 同上 |
| Embedding | 题目去重 / 知识点检索 | 供应商（含**本地模型**）、模型名、API Key、**向量维度**（改动需提示重建 pgvector 索引） |
| 语音（ASR/TTS） | 模拟面试（五期） | 供应商、模型名、Key、采样率、TTS 音色 |

**关键设计**：

1. **连通性自测**：每层保存前可点「测试连接」，发一条最小 prompt 校验 Key / 模型名 / base_url 有效性，回显延迟与 token 用量；失败给明确原因（401 Key 无效 / 404 模型名不存在 / 超时 / 余额不足）。
2. **Key 安全**：配置落 `llm_config` 表（`layer, provider, model_name, api_key_encrypted, base_url, params_json, updated_at, updated_by`），API Key 加密存储（KMS 或应用层 AES，密钥不入仓）；接口**只回显掩码**（`sk-****abcd`），永不返回明文；前端不回传掩码则视为未修改。**一期实现口径（V2.6）**：不接表，配置 / 历史快照 / 审计统一落盘 `apps/api/config/llm.json`（Key 为 XOR+base64 混淆串，原子写；真实文件 .gitignore 忽略，仓内模板 Key 全空），读写边界集中在 `app/llm_config_file.py`，接 PG 后只需替换该模块。
3. **热生效**：变更后经 Redis 发布订阅通知各 worker 重载，**无需重启服务**；进行中的出题任务继续用旧模型跑完，新任务用新配置。
4. **版本与回滚**：每次修改留一条 `llm_config_history`，可一键回滚；因缓存键含模型标识，切模型后旧缓存自然失效，不会新旧口径混杂。
5. **降级预案**：主模型连续失败 N 次（默认 3）自动切 fallback 供应商并在管理端告警，对齐第五章合规第 1 条的降级思路。
6. **权限与审计**：管理端独立登录（不复用 C 端账号体系），角色仅 `admin`；审计日志随配置一同落盘（操作人 / 时间 / 动作 / 分层 / 详情，Key 只记掩码，上限 200 条），除「模型发现」外的动作（修改配置 / 连通性自测 / 版本回滚 / 停用名迁移）全部打点，页面每页 10 条分页呈现。
7. **供应商联动与模型发现（V2.4 新增，V2.5 修订交互）**：供应商以注册表管理（OpenAI / DeepSeek / 阿里百炼 / 智谱 / Moonshot / Gemini / Anthropic / 硅基流动 / OpenRouter / Ollama / 本地模型 / 自定义），**选定供应商即自动回填 `base_url`**（仍可手改，兼容自建网关 / 代理）；**填入 API Key 后自动拉取该账号可用模型，无需点按钮**——输入停顿约 700ms 触发（防抖），并以「供应商 + base_url + Key」为指纹去重，同一组输入只请求一次；Key 为空、回显掩码（掩码 = 未修改）、本地或无需 Key 的供应商均不触发；「拉取模型」按钮相应降级为**「重新拉取」**（强制刷新用）。拉取失败（Key 无效 / 网络不通 / 接口漂移）时回落常用候选并给出可读原因，且**模型名始终允许手动输入**（模型清单变动快，不能只靠拉取）。模型名控件为**自控候选下拉面板**而非原生 `datalist`（后者在部分浏览器点击不展开，用户感知为「点了没反应」）：点击输入框或右侧箭头即展开，可点选、可按输入过滤（输入值已等于某个完整候选时不过滤，否则会把当前选中项自己筛掉）、可点面板外收起，空态区分「正在拉取 / 无匹配候选 / 暂无候选」三档文案。**切换供应商时清空原模型名与备用模型**（它们属于旧供应商，继续用会 404），发现返回候选后若该层尚未选中模型则自动选中第一个候选（本地供应商同理直接选中已下载模型）；已有模型名（含手填自定义名）不被覆盖。注册表声明每家可承接的分层，选了不支持的分层只提示不阻断。
8. **本地模型内置（V2.4 新增）**：可离线运行的模型（一期为向量模型）**直接下载到项目内 `apps/api/models/`**，运行时由服务端从本地目录加载推理，不出网、不计费；Embedding 层默认即指向本地模型（bge-small-zh-v1.5，dim 512）。理由：向量调用高频且无生成质量差异（每次出题要打几百次），本地跑边际成本为 0，且简历 / JD 向量化环节不出网。权重**入仓跟踪**（团队共享、克隆即用，单文件 91MB 低于 GitHub 100MB 上限），需重新下载或新增模型时执行 `python scripts/download_models.py`；下载多源重试（ModelScope → hf-mirror → HuggingFace）并写 `manifest.json` 作为管理端清单数据源。本地模型的「测试连接」为**真实推理**（跑一次向量化并校验同义句 / 无关句相似度区分度），而非配置校验。
9. **边界**：生成式分层（主模型 / 轻量模型 / 多模态 / 语音）不本地部署，仍走云端供应商；本地只承接向量（后续可扩展 rerank）。

### 4.7 文件、缓存与记忆存储（V2.2 新增）

| 存储对象 | 载体 | 设计说明 |
|---|---|---|
| 简历原文件 / 优化版 / 数据导出包 | 对象存储（OSS/MinIO）私有桶 + 服务端签名 URL | `resumes.file_key` 只存对象 key，禁止公网直链；注销时物理删除对象（满足 15 章数据主权承诺） |
| LLM 结果缓存 | Redis（热，TTL 24h~7d）+ `agent_artifacts` 表（冷，长期复用） | **缓存键 = hash(模型标识 + Prompt 模板版本 + 输入内容摘要)**：简历产物挂 resume 版本号，JD 产物挂 security_id；改 Prompt 版本即整体失效，防止新旧口径混杂 |
| JD / 岗位检索缓存 | `jobs_cache` 表（PG），定时任务按 TTL 7 天刷新 | V2.2 修正：取代 boss-agent-cli 的本地文件缓存，服务端多 worker 共享、可水平扩展 |
| 会话记忆（语音面试） | 会话内：LangGraph 内存态（多轮追问上下文）；会话后：`interview_answers` + `interview_turns` 持久化 | 会话结束即固化，复盘报告只读历史转写稿，不再依赖 LLM 会话内存 |
| 用户长期画像（记忆） | **不单独建画像表，按需实时聚合** | 计划生成 / 每日一练出题时，聚合近 30 天的 `user_question_state`（薄弱点）+ `review_schedule`（到期）+ `daily_stats`（节奏）+ `job_pipeline`（面试日程），以聚合摘要作为 LLM 输入——避免维护一份易腐化的画像快照，也缩小个人数据暴露面 |
| 答题事件明细 | `answer_events`（按月分区表） | 全站答对率、掌握度图谱、周报的唯一事实源；`site_question_stats` 是其聚合派生表，可随时全量重算 |
| 会话/对话记录 | `agent_checkpoints` 保留 30 天后清理 | Checkpoint 是任务恢复用的临时记忆，任务终态（成功/失败）落库后即可清理 |

**备份容灾**：PostgreSQL 每日全量 + WAL 归档（RPO ≤ 24h），对象存储跨区冗余；恢复演练列入每期门禁测试项。

## 五、合规与风险

1. **BOSS 数据获取（V2.2 修正口径）**：由**平台运维受控检索账号**（只读）运行 boss-agent-cli 做低频检索，遵守其节流（高斯延迟）与风控机制；不要求用户登录 BOSS，不做批量采集、不做自动化投递/打招呼；页面固定展示数据来源声明（「数据来自 Boss 直聘 · 实时检索 · 缓存 7 天」）。产品上线前需评估平台条款风险，备好降级预案（链接/截图通道切为用户手填 + 粘贴 JD 文本通道兜底）。
2. **简历隐私**：简历文件加密存储，解析文本脱敏后才送 LLM（姓名/电话/身份证/公司敏感信息脱敏）；一键优化产物同样受保护；提供一键删除全部数据。
3. **生成内容准确性**：参考答案标注「AI 生成，仅供参考」；客观题双验证机制。
4. **公司背景信息**：仅聚合公开信息，注明信息时效。
5. **全站统计隐私**：仅聚合数据，低样本不展示，分桶百分位不暴露个体。
6. **语音数据**：面试录音默认不留存，仅保留转写文字稿用于复盘，用户可删除。
7. **公司背景 RAG 数据源（V2.2 补充）**：引擎 C 的公司背景情报仅采信公开可检索来源（官网、公开财报/新闻、百科类），抓取频率受控；入库时记录来源 URL 与抓取时间并在前端标注时效；不存储、不展示任何个人隐私相关的第三方信息。
8. **LLM 供应商数据处理（V2.2 补充）**：脱敏后的简历/转写稿送第三方 LLM 需在隐私协议中明示；优先选择承诺「不用客户数据训练」的供应商；`agent_artifacts` 中的用户产物随注销一并删除。

## 六、研发排期与交付计划（V2.1 重排：Web 先行 → App 后置，分期交付 + 测试门禁制）

### 6.1 排期总原则

1. **先 Web 后 App**：Web 端五个期全部通过验收门禁后，才启动 App/小程序端。App 期复用已验证的后端 API 与业务逻辑，端侧只做实现与适配，风险后移且工作量可控。
2. **分期增量**：每期只交付一组功能，主干功能（一期的基础训练闭环）不被后续新功能扰动；每期结束代码打 tag，作为下一期回归基线。
3. **测试门禁制（每期四步）**：`功能开发 → 开发自测 → 集成/回归测试 → 验收评审`，**门禁不通过不得进入下一期**。
4. **每期准出标准（门禁硬指标）**：
   - P0/P1 缺陷清零，P2 缺陷 ≤ 5 且均有规避方案；
   - 本期核心链路测试用例 100% 通过，**此前所有期次的回归用例 100% 通过**；
   - 性能指标达到第十三章技术指标（出题端到端 P90 < 4 分钟/80 题等）；
   - 验收评审（产品 + 测试 + 开发三方）签字确认。
5. 排期已含每期约 20% 缓冲（用于缺陷修复与回归）；若门禁未通过，下一期顺延，不压缩测试时间。
6. **人力假设（V2.2 补充）**：上述 22 周按 **2 名后端 + 1 名前端 + 1 名测试 + 0.5 名产品** 估算。若团队规模缩减，按期整体顺延（保持测试门禁不被压缩），或砍掉当期 P2 级功能（每期范围表中优先级最低项优先裁剪）。

| Web 二期 | W5~W7 | 学习计划 + 模考 + 简历体检/一键优化 | 一期回归通过 + 模考恢复用例通过 |
| Web 三期 | W8~W10 | 引擎 B + 考点地图 + 每日一练 | 异常矩阵专项通过 + 检索成功率 ≥ 95% |
| Web 四期 | W11~W13 | 引擎 C 三通道 + 求职看板 + 周报 | 三通道 E2E 通过 + 提醒触发 100% |

### 6.5 与 V2.0 排期的差异及核对修正说明

1. **双端并行 → Web 先行**：原 V1.0「双端（Web + 小程序）」改为 Web 五期全部验收后再启动 App，端侧适配风险后移，后端在 Web 期充分验证。
2. **全站统计前移**：轻量答对率统计从 V1.5 前移至 Web 一期（修正「题目详情一期上线但统计服务二期才有的依赖倒挂」）。
3. **复习提醒渠道分段**：Web 期为站内信 + 浏览器通知；小程序订阅消息 / App Push 于 App A1 期接入（修正「推送依赖移动载体但 Web 先行」的断层）。
4. **语音面试拆两段**：后端能力（ASR/TTS/评估）在 Web 五期建成，移动端体验在 App A2 期复用，避免重复开发。
5. **口径统一**：引擎 A 题量统一为「精简 40 / 标准 80 / 深度 120」三档、默认 80（消除 60~100 与 120 的不一致）；模拟考试统一为 20~30 题 / 45 分钟。
6. **门禁制正式化**：每期增加准出硬指标与三方验收评审，测试不通过不顺延压缩，宁可顺延排期。

- App 原生壳（iOS/Android，视小程序 A3 期数据决策）
- 社区面经 UGC + AI 结构化沉淀回题库
- 企业版（校招题库定制）

## 七、核心用户旅程（与原型角色一致）

> 林晓，3 年产品经验，目标「产品经理」岗位。

> 6. 面试后：把实际被问到的新题一键回录，进入错题本循环，看板卡片移入「面试」列等待三面。

## 九、关键交互与体验细节

### 9.1 新手引导与冷启动（首次进入 3 步）

1. **选择目标岗位方向**（可跳过）→ 2. **上传简历或先体验示例题库** → 3. **生成第一套专属题**。
- 未上传简历的用户：提供「示例简历一键体验」（内置 3 份脱敏样例：应届/3 年/转行），30 秒内可刷到题，避免空注册流失。
- 未登录：允许刷示例题 20 题，触发保存进度/错题本时引导微信一键登录。

### 9.2 刷题页交互（对齐原型 P9）

- 选项点击即判对错（练习模式）并震动/变色反馈；答错自动入错题本并 toast 提示「已收录，解析见下方」；
- **答题卡**：数字格区分已答/未答/当前题，「交卷前可修改答案」，点击格位跳题；
- 手势（移动端）：左右滑切换上/下题；长按选项可「标记存疑」；
- Web 端快捷键：A/B/C/D 直接作答，→ 下一题，F 收藏，Enter 交卷；
- 背题模式：默认折叠解析，点击展开；支持「只看错题相关章节」。

### 9.3 模拟考试异常恢复

- 断网/杀进程：答题进度每题实时落库（`exam_records.detail_json` 增量保存），重进考试弹出「恢复上次考试」；
- 倒计时暂停规则：仅当 App 退到后台 > 10 分钟才暂停计时并标记，防止利用暂停查资料；模考成绩标注「含暂停」；
- 交卷前二次确认未完成题数；允许「只交已答」。

### 9.4 出题等待体验（长任务）

- 出题 60~120 题为分钟级任务：SSE 流式推进度条（「已生成 23/80 题 · 当前维度：项目深挖」），**已生成的题立即可刷**，无需等全部完成；
- 生成失败维度自动重试 2 次，仍失败则跳过该维度并在报告中明示「场景设计维度生成失败，点击重新生成」；
- 中途可退出，后台继续，完成后推送通知。

### 9.5 语音模拟面试交互（V2.0 新增，对齐原型 P7）

- 进入会话先做麦克风权限检测，未授权提供文字模式降级；
- ASR 流式转写文字稿实时上屏，答完可「重新作答」（丢弃当前稿）或「提交回答」触发评估；
- STAR 四维分与命中关键词在提交后 3 秒内返回（轻量模型评估，主模型仅用于最终复盘报告）。

## 十、空状态、加载与异常流程

| 场景 | 表现 | 处理 |
|---|---|---|
| 无简历 | 简历分析页空态 | 引导上传 + 「先用示例简历体验」按钮 |
| 无错题 | 错题本空态 | 「太棒了，去刷一套模考检验一下」引导 |
| 出题失败 | 任务卡错误态 | 一键重试；额度不扣减 |
| BOSS 风控命中 | 检索层返回恢复指令 | 产品内提示「岗位检索暂不可用，约 X 分钟后自动恢复」，期间引导先用简历引擎或系统题库 |
| 截图识别失败 | 置信度 < 阈值 | 返回识别出的候选岗位列表让用户手动确认，或提示「改贴岗位链接」 |
| 链接失效/岗位已下架 | detail 取不到 JD | 使用截图通道或引导用户粘贴 JD 全文，「手动粘贴 JD」作为终极兜底通道 |
| JD 缓存过期 | TTL 7 天 | 重新拉取并提示「该岗位 JD 有更新，题库可一键刷新」 |
| 简历解析失败（扫描件模糊） | OCR 置信度低 | 高亮未识别区段，引导用户手动补录技能栈/项目经历，补录内容同样参与出题 |
| 语音不可用（权限/弱网） | 面试页自动降级 | 切换文字输入模式，评估链路不变 |

## 十二、题目质量反馈闭环（UI 落地）

- 每题右下角常驻「反馈」入口（题目有误 / 答案有误 / 解析看不懂 / 题目太简单）；

- 面试后回录：看板岗位标记「已面试」时引导「录一道实际被问到的题」，AI 结构化后进入个人题库并可选匿名贡献到公共面经池（V2.5 UGC 冷启动机制）。

## 十三、数据指标体系

- **北极星指标**：周人均「有效答题数」（作答且查看解析计 1 次）。
- **获客漏斗**：落地页 → 体验示例题 → 注册 → 上传简历 → 首套题生成完成（核心转化：上传简历 → 生成完成率 ≥ 70%）。
- **留存**：次日/7 日留存、连续打卡率、今日计划完成率、错题复习完成率（目标 ≥ 60%）。
- **质量**：客观题答案双验证一致率（≥ 98%）、题目反馈率（< 2%）、套题刷完率（≥ 35%）、STAR 评估返回率。
- **商业**：免费转付费率、ARPU、单用户月均 LLM 成本（缓存命中率 ≥ 60% 时可控）。
- **技术指标**：出题端到端 P90 时长（< 4 分钟/80 题）、BOSS 检索成功率（≥ 95%）、ASR 转写首字延迟（< 800ms）。

## 十四、商业化（MVP 后置，先埋点）

- **免费版**：1 份简历、每月 2 次引擎出题、基础错题本、每日一练。
- **Pro（订阅）**：不限出题次数、引擎 B/C、AI 模拟面试（语音）、AI 一键优化简历、匹配度报告、学习周报、错题导出。
- **单次付费**：面试冲刺包（指定岗位定向冲刺包 + 3 场语音模拟面试），面向非订阅用户的临门一脚场景。
- 所有付费点先以「额度+引导页」灰度验证付费意愿，不急于正式收费。

## 十五、账号、隐私与数据安全（补充）

- 登录：微信一键登录（小程序/公众号 OpenID 打通）+ 手机号验证码（Web）。
- 数据主权：用户可导出全部个人数据（简历/题库/错题/报告，JSON+PDF），可一键注销并物理删除（含 LLM 侧会话记录，7 天内完成）。
- 简历脱敏：送 LLM 前替换姓名/电话/邮箱/身份证/公司敏感信息为占位符，展示层还原。
- 语音数据：面试录音默认不留存，仅存转写文字稿，可随时删除。
- 未成年人：产品面向求职者，注册协议声明 16+。
